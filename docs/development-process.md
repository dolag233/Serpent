# Serpent 开发与质量流程

> 状态：生效
> 日期：2026-07-12

## 原则

每个开发切片必须同时交付代码、测试和开发记录。聊天记录不视为开发文档；重要事实必须写入仓库本地 `docs/`。开发记录用于回答：为什么这样实现、实际完成了什么、如何验证、还剩什么风险，以及下一位开发者怎样继续。

`docs/`、`AGENTS.md`、`CLAUDE.md`、Cursor 与 Copilot 指令都进入版本控制，作为所有开发工具共享的工程记忆。若使用远端 Issue 或 PR，还需要把验收摘要和关键结果同步到远端描述。

## 每个切片的文档集合

```text
docs/
  implementation/
    NNNN-<slice>-vertical-slice.md   # 实施规格与验收条件
  development/
    NNNN-<slice>-development-log.md  # 开发过程与技术记录
  reviews/
    NNNN-<slice>-code-review.md      # Standards / Spec 双轴审查
  qa/
    NNNN-<slice>-qa-report.md        # 自动化和人工 QA 证据
```

只有出现难以逆转、原因不直观且确实存在权衡的决定时，才新增或替代 `docs/adr/` 中的 ADR。

## 开发记录要求

开发日志在切片开始时创建，并在开发过程中持续更新，不在结束时凭记忆补写。至少包含：

- 切片规格路径、分支、基线 SHA 和当前提交。
- 开始时间、当前状态和最后更新时间。
- 已完成的垂直行为。
- 采用的公共测试接缝。
- 功能变更同步更新了所有受影响的自动化测试；若规格变化导致旧测试失效，必须同时更新 fixture、断言和测试说明，并记录迁移原因。
- 重要实现决定及理由。
- 与规格的偏离、偏离原因和是否获得确认。
- 执行过的关键命令及结果摘要。
- 遇到的失败、根因和解决方式。
- 当前已知问题、技术债和后续工作。
- 重要文件入口，方便下一位开发者继续。

开发日志记录结论和证据，不复制完整终端输出，不记录密钥、凭据、个人信息或无关调试噪声。

## QA 报告要求

QA 报告至少包含：

- 被测分支、提交 SHA、构建环境和构建产物。
- lint、类型检查、单元测试、集成测试和冒烟测试结果。
- 每个平台的人工 QA checklist、实际结果和证据位置。
- 失败用例、复现步骤、严重程度和处置状态。
- 未执行项目及原因，例如暂时没有 Windows runner。
- 最终结论：通过、有条件通过或不通过。

“没有执行”不能写成“通过”。因环境缺失未执行的项目必须明确保留为交付风险。

### 核心用户旅程门禁

- **数据兼容性是发布级门禁（Serpent-033e / ADR-0028）**：任何版本都必须完全兼容旧版本数据——新代码打开旧库自动无损迁移、升级后全功能可用是硬目标；只读降级只是兜底。迁移只加不改（禁删改现有表/列/索引/触发器）；每个迁移的验收必须证明「旧版本库 → 迁移后全功能可用」（数据不丢、语义不变、派生数据可重建）；违反不合并。涉及 `MIGRATIONS` / schema 变更的提交，代码审查必须核对此条。
- 浏览、缩略图解码、放大预览、导入、搜索和删除属于核心用户旅程。任何影响 Renderer、Preload、Main、Worker、CSP、自定义协议或打包资源的改动合并后，都必须重新执行这些旅程的 Electron E2E，不能只依赖所属模块的单元测试。
- UI 冒烟测试必须验证用户获得了有效结果，不能只验证容器或 DOM 元素存在。例如图片必须满足 `complete && naturalWidth > 0`，视频必须至少到达 `HAVE_METADATA` 且宽高非零，下载必须校验文件内容而非只校验进度条出现。
- 持久化功能至少覆盖“创建/导入 → 关闭资源库或应用 → 重新打开 → 再次使用”的路径；只测本次会话新建数据不能代表已有资源库兼容。
- 测试替身必须核对会影响真实工具执行的关键参数。FFmpeg/OIIO/系统命令除检查“被调用”外，还要检查关键 option 名称和值，并保留一条真实二进制或打包产物冒烟路径。
- 共享工作树或多 agent 扇出结束后，由主 agent 在最终合并状态执行一次 `npm run verify:mainline`。该命令未通过时停止功能扩展，切片状态回到 `fixing`，不得以各子任务曾单独通过代替最终门禁。
- 功能变更后的测试同步是完成定义的一部分：测试失败需要先判断是实现回归还是规格/fixture 已变化；前者修复代码，后者更新测试和文档，二者都不能留作“测试落后”的已知红灯。
- 每个 Electron E2E 应使用唯一的临时 `userData` 目录，禁止默认读写开发者真实配置目录。只有显式验证完整重启或单实例语义的同一条用例，才能在该用例内共享一个显式传入的 profile。`SingletonLock` 等启动冲突属于测试基础设施失败，必须修复隔离原因，不得通过重试将其隐藏。

### 大功能 UX / UI 人工门禁

- 每个较大功能、核心用户旅程改动或跨多个界面的 UX 更新，在进入 accepted 前必须启动真实 Serpent 桌面应用，由主 agent 使用 Computer Use 完成至少一条代表性用户旅程；不能只查看浏览器 DOM、组件 story 或测试替身。
- 必须截取并检查该功能影响的关键界面状态。按实际范围覆盖进入态、工作态、完成态，以及相关的空、加载、失败状态；没有对应状态时可明确写“不适用”。
- 截图检查至少包含：信息层级、间距与对齐、裁剪和溢出、文字可读性、控件可发现性、媒体适配、焦点位置、跨面板数据一致性，以及窗口尺寸变化后的布局。
- 截图和 Computer Use 是产品/视觉验收证据，不替代 E2E、解码断言、性能和错误日志验证；自动化全绿也不能替代真实 UX 操作与视觉判断。
- QA 报告记录操作路径、数据样本、截图绝对路径或仓库证据路径、观察结果和未解决问题。若截图包含用户隐私、绝对路径或敏感数据，先使用专用测试资源库或脱敏样本，不把敏感截图提交进仓库。
- 主 agent 以总产品经理身份对最终可用性和视觉质量负责。编码、自动化 QA 和代码审查可以委派，但较大功能是否达到产品验收必须由主 agent 在最终合并状态亲自确认。
- 若当前 agent 环境不具备 Computer Use 或等价的真实桌面控制能力，不得把该门禁视为可跳过，也不得将切片标记为 `accepted`；必须在 QA 报告中记为未执行，并交由具备该能力的主 agent 或人工 QA 补验。

### 持续人类功能验收队列

- `docs/qa/human-acceptance-checklist.md` 是产品负责人逐项验收已经具备功能性的用户能力的唯一队列。它不替代切片 QA、平台矩阵或发布完成定义。
- 验收项必须是人类可以独立操作并给出明确通过/不通过结论的最小功能；大功能应拆成多个条目，避免其中一个缺口掩盖其余已完成能力。
- agent 只有在功能路径存在、当前合流状态的相关自动化通过、该条目范围内没有已知阻断、操作步骤和预期结果明确时，才可把项目加入“待人类验收”。旧包、旧提交、局部工作树结果或未执行平台不能作为当前条目的就绪证据。
- agent 在开发过程中达到上述条件时立即更新清单，并与代码放在同一提交；不得等到交接或会话结束再批量追记。阶段性汇报必须列出新增/变更的验收项 ID。
- “人类验收通过”是用户控制状态。agent、自动化、代码审查或 Computer Use 均无权代替用户确认。用户报告缺陷后，当前 agent 必须立即把对应条目标为“人类验收不通过”或“已撤回”，记录原始反馈、日期和修复跟踪位置。
- 尚有已知阻断的范围放在清单的“暂不可验收”区，不得为了显示完成度进入待验收队列。修复后按新的代码基线和步骤重新进入队列。

## 错误可观测性

- 所有返回给用户的失败必须包含具体、可操作且不会泄漏绝对路径或内部实现的原因；不能只显示“操作失败”或“导入失败”。
- 系统错误至少区分权限不足、目标文件系统路径限制、磁盘空间不足、只读文件系统、源文件消失或变化、符号链接/特殊目录项以及磁盘 I/O 错误。
- 每个用户可见失败都必须在持久应用日志中留下对应诊断，包含时间、操作范围、错误类型、系统错误码、堆栈和 cause 链。完整路径只进入本地日志，不跨 IPC 暴露给 Renderer。
- QA 报告需要记录日志文件位置，并至少验证一次“界面安全原因 + 日志完整诊断”的对应关系。

## 代码审查记录要求

代码审查报告分别保留：

- Standards：仓库规范、架构边界和代码异味发现。
- Spec：缺失需求、错误实现和超范围实现。
- 每项发现的处理状态、修复提交或接受理由。
- 修复后的复审结果。

报告必须固定审查基点和 diff 范围，使审查可以复现。

## 状态流转

```text
ready
  → implementing
  → automated-verification
  → code-review
  → qa
  → fixing
  → accepted
```

允许从 code-review、qa 或 accepted 前的验收检查返回 fixing。每次状态变化都更新开发日志。

## 完成定义

一个切片只有同时满足以下条件才能标记完成：

- 规格内行为已实现，未确认的范围没有偷偷加入。
- 约定的自动化测试通过。
- 双轴代码审查已完成，阻断问题已解决。
- 要求的平台 QA 已执行；未执行项被明确标记并获得接受。
- 开发日志、代码审查报告和 QA 报告完整且互相引用。
- 所有偏离规格的决定已记录。
- 已知问题和下一步清晰可执行。
- 代码已形成可审查提交；是否推送和创建 PR 由用户另行授权。

## 第一切片启动时应创建

```text
docs/development/0001-library-shell-development-log.md
docs/reviews/0001-library-shell-code-review.md
docs/qa/0001-library-shell-qa-report.md
```

开发日志在第一行代码之前创建；审查和 QA 文档可以先建立骨架，随后随流程填写。
