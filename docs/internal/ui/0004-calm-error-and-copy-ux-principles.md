# UI direction 0004: Calm errors and copy UX principles

> Status: active product/UX constraint  
> Date: 2026-07-25；2026-08-18 补充「必须写清原因与解法」  
> 关联：TOAST-003/005、ERROR-LIB-001、`FatalAlertDialog`、`Serpent-rk65`、`Serpent-n5iu`、`Serpent-4f44f1`、REQ-EXT-002（扩展已无配对码）

Serpent 的错误与确认文案应**说清楚发生了什么、为什么、下一步能做什么**，而不是用夸张语气让用户紧张，也不是用空泛失败句把用户打发走。用户已经在处理自己的素材；产品语气是冷静、具体、可行动的同事，不是警报器，也不是「失败了，请重试」。

## 1. 禁止「耸人听闻」的标题

以下表述**不得**作为对话框或阻塞提示的默认标题：

- 「严重错误」「致命错误」「Critical error」「Fatal」
- 暗示灾难、崩溃、数据已毁的措辞（除非事实已核实且用户必须立即知晓）

阻塞对话框（`FatalAlertDialog` / `role="alertdialog"`）的标题必须**点名操作**：

| 场景 | 中文标题示例 | 英文示例 |
|------|--------------|----------|
| 打开资源库失败 | 无法打开资源库 | Couldn't open library |
| 创建资源库失败 | 无法创建资源库 | Couldn't create library |
| 导入失败 | 导入失败 | Import failed |
| 继续导入失败 | 无法继续导入 | Couldn't continue import |
| 校验导入失败 | 无法校验导入 | Couldn't validate import |
| 导入资源库包失败 | 无法导入资源库 | Couldn't import library |
| AI 批量全失败 | AI 分析失败 | AI analysis failed |

标题可以点名操作；**正文禁止只重复标题**。禁止把「无法打开资源库」「Serpent 无法完成这项操作」当成完整错误。

## 2. 阻塞弹窗 vs 顶部 error 条

| 级别 | 何时使用 | 标题 |
|------|----------|------|
| **静默** | 用户试探性操作、无实际效果可预期（如空剪贴板粘贴） | — |
| **顶部 error 条** | 单次操作失败、用户可继续工作 | 无独立标题；正文即原因 + 解法 |
| **阻塞对话框** | 必须确认后才能继续当前流程（开库失败、导入管线失败、AI 批量全失败） | 具体操作名（见上表） |

常规失败**默认不用**阻塞窗；只有流程确实卡住、需要用户读完后点「知道了」时才用。

## 3. 正文必须详细：原因 + 解法（强制）

只说「xx 无法完成」「xx 无法打开」「操作失败」对排障没有帮助。每一条用户可见错误的**正文**必须同时包含：

1. **原因**：发生了什么、系统观测到什么（权限、路径不存在、磁盘满、数据库无法在 NAS/SMB 上加锁、服务器返回 401、文件被占用等）。
2. **解法**：用户现在可以采取的至少一条具体行动（换本机磁盘、检查写权限、清理空间、关闭占用程序、打开诊断日志、升级 Serpent、改用 WebDAV 同步等）。

资源库相关错误是最高优先级：开库、建库、打开最近库、Eagle/Billfish 转换、同步库。这类失败已经有真实用户反馈；不得再落到 `INTERNAL_ERROR` 或「无法写入所选位置」这类无差别句子。

禁止：

- 「Serpent 无法完成这项操作，请重试。」（无原因）
- 「Serpent 无法完成这项操作，请查看日志了解详细原因。」（把诊断推给用户，界面自己没说）
- 「资源库操作失败。」「打开最近资源库失败。」（无对象、无原因、无解法）
- 未核实损坏时写「数据库已损坏 / 数据已毁」

允许的最后兜底（仅当 errno / SQLite code / 领域码都无法分类时）仍须告诉用户：打开应用内「诊断日志」查看本次记录，并把资源库复制到本机磁盘后再试。

正文来源必须是 `error.code` + 可选 `error.reason` 的 i18n 映射（`messageForPublicError` / `toMessage`），不得把内部 `Error.message`（可能含路径）直接展示给用户。

## 4. 避免无端焦虑

1. **不说用户的错**：避免「你做了什么导致…」；用中性陈述（「无法读取该文件」「路径不存在」）。
2. **不夸大后果**：未丢失数据时不要写「数据已损坏」；区分「操作未完成」与「库文件无法读取」。开库失败后 Serpent 会尝试备份恢复时，要写「将尝试从备份恢复」，不要写「库已经没了」。
3. **预期内的空结果不打扰**：空剪贴板粘贴、取消文件选择（`CANCELLED`）不弹窗、不 error 条。
4. **同一失败不叠多层**：已有阻塞对话框时，不再叠 toast；同一批 AI 失败只弹一次连接类对话框。

## 5. 配对、鉴权等已废弃概念

产品已取消浏览器扩展配对码（`Serpent-1cxv`）。UI 与设置文案**不得**再提「配对码」「配对」「pairing code」；扩展说明只描述：保持 Serpent 运行、打开资源库、安装/加载扩展即可。

## 6. 实现检查清单

新增或修改错误路径时：

1. 标题是否具体到中性的操作名？
2. 正文是否包含**原因**和**至少一条解法**，而不是「无法完成 / 请重试 / 请查看日志」？
3. 正文是否来自 `error.code` / `error.reason` 映射，且未泄漏绝对路径？
4. 资源库失败是否映射到 `LIBRARY_*` / `DISK_FULL` / `NOT_A_LIBRARY` 等具体码，而不是 `INTERNAL_ERROR`？
5. SQLite `IOERR`（尤其 NAS/SMB）是否映射为网络共享不支持，而不是「无法写入」？
6. 空剪贴板、用户取消是否静默？
7. i18n 中英文是否同步、无「严重/Critical」默认兜底？
8. 是否更新 `docs/internal/qa/human-acceptance-checklist.md` 可验收步骤（若为用户可见增量）？

## 7. 变更流程

1. 产品或 UX 在本文件或 backlog 补充约束。  
2. 实现：`dialog.blockingError.*` 标题键 + `showBlockingError(title, message)`；Worker 经 `publicErrorForWorkerFailure` / `classifyUnknownFailure` 产出公共码。  
3. 全仓搜索 `严重`、`Critical error`、`无法完成这项操作`、`setFatal(` 无标题调用。  
4. Windows / macOS 各抽一条失败路径人工扫一眼语气，**尤其开库/建库**。
