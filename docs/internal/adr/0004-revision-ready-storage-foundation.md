# ADR-0004：底层采用可演进到同步的修订模型

- 状态：已接受
- 日期：2026-07-11

## 一句话解释

不要把“这项资产”直接等同于“磁盘上的这个文件”。资产是长期不变的档案卡；用户替换文件内容时，相当于给这张档案卡换了一份新附件。MVP 记录附件已经变化，但在提供可见的版本管理能力前不长期保留旧附件字节。

例如，用户把 `logo-final.png` 加入 Serpent，后来又用新版文件替换它：

- 它仍是同一项资产，Label、描述、标签、评分和所在合集不变。
- 新旧两个文件内容是这项资产的两次修订；修订记录不保证旧文件字节仍存在。
- 缩略图和 AI 识别结果属于具体文件内容，新版需要重新生成。

MVP 界面不需要出现“版本历史”。这个设计只是避免替换文件、生成预览和未来多设备同步时互相覆盖或关联错数据。

## 背景

MVP 不提供面向用户的版本管理，但长期方向包含集中存储、自动同步和团队资产库。竞品与相邻系统调研表明，自动同步若没有稳定资产身份、修订基准校验和冲突保全，会产生静默覆盖风险。

详见[创意资产的版本、同步、锁与审批](../research/asset-versioning-and-sync.md)。

## 技术表达

从 MVP 开始在数据层区分：

- `Asset`：稳定的逻辑资产身份及当前修订指针。
- `Revision`：一次内容修订，记录父修订、来源、时间和对应内容对象。
- `Blob`：由内容哈希标识的不可变文件内容。
- `AssetMetadata`：Label、描述、标签、评分、色卡等跨内容修订存在的资产级元数据。
- `RevisionArtifact`：缩略图、代理、波形、技术元信息和内容级 AI 结果等属于特定修订的衍生物。

MVP 不必展示版本列表、比较、审批或锁定界面。修订层首先用于安全替换过程、衍生物失效、内容去重及未来同步兼容。客户端替换完成后，旧内容不作为可恢复历史长期保留。

## 理由

- 文件名、Label、目录位置和内容都可能变化，不适合作为稳定资产身份。
- 缩略图、视频代理和内容分析结果取决于具体字节内容，应随修订失效或重新生成。
- 未来同步可通过基准修订检测并发修改，并保留双方内容，而不是最后写入者静默覆盖。

## 后果

- MVP 的存储层和索引层会比单一文件表略复杂。
- 链接文件夹和被外部覆盖的托管文件可以形成修订记录，但 MVP 不复制被覆盖前的旧字节。
- 内容哈希、垃圾回收和 Blob 校验策略仍需设计；可见版本管理上线时需要另行决定历史内容保留策略。
- 接受本 ADR 不等于把版本管理功能加入 MVP。
