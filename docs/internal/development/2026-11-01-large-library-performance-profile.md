# 大型真实库性能基线：导航与测量有效性

状态：分阶段优化中，未完成整体验收。分支 `dolag_dev`，起点 `77aede48`。本文只记录一台 Windows 开发机上的当次真实资源测试；资源名称、路径和文件名不入库。

## 样本与方法

- 获授权的本地真实 Serpent 库：28,972 个资产，116 个合集，无托管或链接文件夹。测试前后资产数均为 28,972；本轮不执行删除操作。
- 第二组获授权的真实图片目录含 15,473 个可登记文件。测试把它链接到临时新库，源目录只读；每次关闭独立 Electron 后清理本次创建的临时库和 userData。临时库位于另一个目录，测试先验证两棵目录不重叠、目标盘有至少 10 GiB 空间，清理时拒绝越界路径和 reparse point。
- Electron E2E 使用隔离 `SERPENT_E2E_USER_DATA_PATH` 并保持窗口隐藏；输出和日志写在本机临时目录。性能测试窗口使用 opt-in 离屏渲染，以便隐藏时仍产生帧。源库路径由运行者通过环境变量提供，不写入源码或报告。
- 执行命令：`node scripts/run-e2e.mjs tests/e2e/navigation-profile.test.ts --reporter=line`（设置 `SERPENT_PROFILE_LIBRARY`、`SERPENT_PROFILE_OUT`、`SERPENT_PROFILE_WHEEL_MS=2500`、`SERPENT_PROFILE_SWITCHES=2`），以及 `node scripts/run-navigation-benchmark.mjs`（设置 `SERPENT_NAV_BENCH_ITERATIONS=2`、`SERPENT_NAV_BENCH_WHEEL_MS=2000`、`SERPENT_NAV_BENCH_SETTLE_MS=5000`、`SERPENT_NAV_BENCH_DECODE_BUDGET_MS=5000`）。两类导航 E2E 各 1 passed。
- 链接目录命令：`node scripts/run-e2e.mjs tests/e2e/linked-real-performance-profile.test.ts --reporter=line`，仅在设置 `SERPENT_LINK_PROFILE_SOURCE` 与 `SERPENT_LINK_PROFILE_TEMP_PARENT` 时运行。最近一次 1 passed（29.3 秒），并检查可见图片实际解码。测试过程中发现最初选取的目录有 685 个下级文件夹，文件夹卡片行把图片网格排到约 25,000 像素以下；旧测试误把“图片卡片存在于 DOM”当成“图片进入视口”，产生解码等待超时。现要求子目录无下级文件夹、至少 100 张图片且图片占直接文件的 80% 以上；选中同一真实源里 282 个直接文件的目录量图片滚动。文件夹密集场景单独保留为待分析项。这是**测试口径错误的修正**，不能算产品修复。

## 测量陷阱与修正

普通隐藏窗口的 `requestAnimationFrame` 约每秒一次。首轮 2.5 秒滚动只采到 4 帧、帧间隔约 1009 ms；图片首帧被量成约 1.2 秒。动态或构造时关闭 `backgroundThrottling` 仍未解除这个现象。以此声称产品滚动卡顿或预览慢都无效。

离屏渲染后，同样隐藏的窗口在 2.5 秒采到 157–160 帧，卡片节点和媒体 URL 确实变化。导航 profile 在范围切换后曾停留于仅 34 个资产、不可滚动的合集；测试现先返回全库，再量滚动，避免把静止页面当成流畅滚动。旧导航基准还把只在后续分页发出的 `browse-page` 事件当作首屏提交信号，曾将正常切换错误记为超时；现以目标范围激活及卡片集合提交计时。

这些“前后”数字是**测量方式的纠正**，不是产品优化带来的加速。离屏合成不等同真实显示器呈现，最终视觉流畅度仍需真实桌面验收。

## 链接目录入库：已优化的阶段

原实现先遍历约 1.5 万个真实文件，再在单一事务中逐个插入资产、版本、更新当前版本，并调用通用搜索同步函数。新资产还没有标签和描述，但该函数仍为每个文件查询资产/版本、旧搜索行、标签等表。现用同一事务里的已知快照直接生成初始搜索行，保留 FTS5 触发器；资产插入时就写入当前版本 ID，再插入对应版本，不产生额外的资产更新。当前版本字段没有指向版本表的外键，事务提交前版本行已存在；搜索词、空元数据、大小标签及路径字段由 Worker 测试核对。

| 同一真实目录，隐藏离屏 Electron | 优化前 | 优化后 | 边界 |
| --- | --- | --- | --- |
| 链接操作到根节点出现在侧栏 | 11.6–12.5 秒 | 7.2–8.8 秒 | 约 24–42% 缩短；多次顺序运行，受磁盘缓存和系统负载影响 |
| 扫描结束到索引提交进度事件 | 约 8.5 秒 | 约 4.5–5.7 秒 | 进度事件到达 renderer 的时间，不等于独立 Worker CPU 计时 |
| 进入无下级文件夹的 282 文件目录到首张图片卡片 | — | 176–356 毫秒 | 未计入等待图片解码；80% 可视图片解码曾用时 1011–1267 毫秒，最近一次为 72 毫秒，波动尚未解释，不能宣称稳定达到 500 毫秒目标 |

本次只优化链接**首次入库**，没有测得刷新现有目录、创建/删除子目录或旧库切换的前后加速。真实源无删除；资产总数前后保持 28,972。

## 视频探测去重：局部实现与风险

同一 revision 的 poster 与 metadata job 原会分别启动 ffprobe；现在并发请求共享一次完整探测，poster 可复用未失效且 generator 匹配的已就绪 metadata。更换 revision 后重新探测；后续 metadata job 因结果已就绪而取消时仍发 Inspector 更新事件。独立审查发现最后一个等待者取消后，旧探测可能仍在退出，此时新请求不能复用已中止的 promise；现对视频探测和共用等待机制的联系表生成都跳过已中止的条目，旧任务的 finally 只移除属于自己的条目。回归测试保持旧 ffprobe 未结束，取消 metadata job 后让 poster 立即发起第二次完整探测。`tests/worker/video-exr.test.ts` 的定时 mock 将同一 revision 探测次数从 2 次断言为 1 次；固定 8 ms 的 mock 等待从累计 16 ms 变为 8 ms，**不代表真实媒体提速**。

获授权库有 214 个可读 MP4。按文件大小抽 5 个（约 0.1–440 MiB）各交替运行旧 duration-only 与新 full ffprobe 两轮；预热后旧方式为 30.1–48.4 ms，新方式为 30.1–47.2 ms，退出码均为 0。首次进程冷启动另有一次旧方式 1306 ms。样本少且只测 ffprobe CLI，不足以证明 poster 端到端延迟或各种编码格式无回归。

## 仍卡顿的真实图片滚动

无下级文件夹的真实目录含 253 个 JPG、17 个 JPEG、10 个 PNG、2 个 PDF；文件大小中位数约 0.85 MiB，p95 约 5.28 MiB。探针曾把同一图片插入时的 `childList` 与 `src` 属性记录重复计数，且重置阶段没有重置按元素记录；现按每阶段的元素与 URL 绑定去重，旧 URL 次数不可再作性能证据，也不能当成网络请求数。最近一次首趟 2.5 秒滚动采到 103 帧，p95 帧间隔 60.6 ms、最大 115.5 ms、1 个 51 ms 长任务、45 个图片元素/URL 绑定观察、90 个卡片槽创建，发生一次 browse request/result/page；反向 142 帧、p95 39.7 ms、0 长任务、91 个绑定观察、0 个新卡片槽、0 分页。回到顶部再走同一正向范围，缓存页下 151 帧、p95 41.3 ms、0 长任务、117 个绑定观察、125 个新卡片槽、0 分页。静止对照 p95 18 ms、0 长任务。此前多轮首趟 p95 为 68.4–85.7 ms，静止对照曾为 17.6–31.4 ms，系统负载有变动。CDP CPU 采样已加入同一真实旅程，首趟与热趟的高自耗时函数仍是压缩后的打包名称，暂不能可靠映射到源码。**首次分页与摘要合并是长任务的首要嫌疑**：同向复走仍有更多图片绑定和卡片挂载，却没有长任务；这只是同一会话中的相关性，尚未用 CPU 归因证明具体函数。不能从前述合集滚动 19.2 ms 推断真实图片目录流畅。下一步应定位分页提交的主线程成本，决定提前预取或缩小状态更新范围，再以相同滚动路径做前后对比；真实显示器呈现仍须独立验收。

## 跨半库滚动条跳转：本轮追加定位

用户报告：已有优化后，在另一约 2.9 万资产的真实库中，从滚动条 5% 直接跳到 55% 仍等待 1–3 秒以上。只读检查该库时，约 2.89 万个成功的缩略图任务、当前无排队或运行任务，绝大部分图片已有就绪缩略图；缺少就绪缩略图的在库资产约 216 个。符合原图直出限制的图片约 2.42 万张，但已就绪的缩略图在卡片 URL 选择中优先，抽样统计的缩略图中位数约 12.7 KiB，原图中位数约 115.5 KiB。因此这个等待不能归因于“正在生成预览图”，也不能靠改成全量原图直出来解决。

旧实例日志出现一条 `media.get-artifact-paths` 排队约 3953 ms；同时资源库打开对账运行约 8280 ms，原生拖拽信息预取运行约 2925 ms。冷位置的卡片须等 Main 向 Worker 取得缩略图路径后才能读图片字节；这条路径查询与拖拽预取同属 `background-primary`，原调度器只能在对账之外放行一个 primary owner。新增受限的可见路径读槽，在已有一个 primary owner 时仍允许一个路径查询入场；其他 primary 继续串行，调度器的 JS/SQLite 同步步骤仍由单线程执行。`tests/unit/interactive-scheduler.test.ts` 的确定性竞争测试在修改前失败、修改后通过，证明路径查询不必等拖拽预取完全结束。日志是相关性证据，尚非用户当前窗口的前后耗时对比。

同一真实库的隔离本地副本上，瀑布流跳转基准曾在 55% 显示“57 ms 完成”，但没有发出目标位置的浏览请求，实际滚动位置回到 0；旧门禁只看旧卡图片已解码，属于误报。测试现必须检查实际滚动比例到达目标（误差不超过 2%）。追踪发现延迟的 `scheduleAnchorRestore` 把打开时记录的 `scrollTop=0` 再写回来；新逻辑在用户滚轮、指针、触摸或稳定布局下的大幅滚动到来时取消旧锚点恢复，同时在内容高度暂时塌缩时仍保留恢复能力。虚拟布局的几何锚点也改为通过索引模型定位，不再扫挂载的 DOM 槽位。

验证命令：`node scripts/run-e2e.mjs tests/e2e/large-library-scroll-benchmark.test.ts --reporter=line`，设置隔离真实库副本、隐藏离屏窗口、跳点 `0.05,0.55`，最终 1 passed。5% 目标实际到达 5.0003%，32/32 张可见图片解码约 263.5 ms；55% 目标实际到达 54.9981%，33/33 张可见图片解码约 375.8 ms。两次各发生一波浏览请求。曾试图在同一隐藏窗口里用自动化鼠标拖动原生滚动条，但输入未移动滚动位置，这两次失败样本（55% 实际仍约 0–5%）不能用于速度判断；已撤下该实验代码。有效结果仍是程序设置滚动位置、预热的本地副本、无真实显示器输出，不能代替原窗口在后台任务竞争下的 1–3 秒旅程；旧基准口径有误，不能把本轮结果写成可信的百分比提速。`tests/unit/canvas-reflow-restore.test.ts` 覆盖“晚到的跳转优先”与“布局塌缩仍恢复”。真实滚动条手势、原窗口复验及独立审查仍待完成。

同一命令不指定跳点时，按固定 10 次远距离位置重跑：第一次 10/10 在 500 ms 内，全部解码 p50 405.8 ms、p95 475.3 ms；最后一处短内容视口测量修正后的当前代码第二次为 **9/10**，p50 327.2 ms、p95 542.7 ms。未达标样本实际到达 15.1% 目标位置，分页在 10.3 ms 发出、116.2 ms 返回并应用，约 173.8 ms 挂载 30 张卡；一张图片约 309 ms 解码，其余大批图片在 524.8–542.7 ms 才完成，期间有 3 个长任务、最长 59 ms。当前数据指向媒体路径读取/解码尾部仍有波动，无法把严格 500 ms 目标记为稳定通过，也不能仅凭这一次把瓶颈唯一归因于 Worker 或磁盘。

2026-11-02 用户在原窗口复验约为 1.5 秒，仍不通过。进一步在同一隔离副本测分段：跳转后分页多数在 44–130 ms 返回，全部可见卡片在 105–197 ms 挂载；首张图片约 345–514 ms 解码。两次 5%→55% 的隐藏离屏程序跳转，分页分别用 289/64 ms、卡片挂载 337/135 ms、全部图片解码 619/515 ms。Renderer CPU 采样的主要自耗时包括 `getBoundingClientRect`，但未出现接近 1.5 秒的卡片排列段；这组证据不支持把原窗口延迟主要归因于排列。旧 Worker 日志有一次拖拽信息预取运行 1517 ms，期间可见预览路径查询的入队到回调约 91–247 ms。原生拖拽预取原来在每次分页返回后取前 100 个资产，但远跳后的实际视口可在该页靠后的位置；这批工作可能一张可见卡也没覆盖。曾尝试把后续分页预取改为真实可见资产上报后延迟 50–600 ms，但可见图片的严格门禁没有改善，且快速原生拖拽可能等不到缓存，因此已撤回，保持原来的分页预取与指针按下补队。仅将 Worker 拖拽路径验证改为有界异步，使一批文件检查不再独占事件循环，并为关闭资源库时仍在运行的预取加代次屏障。一次新日志的拖拽批次运行 7.64 ms，不能据此断言所有库和磁盘都达到该值。

曾将批量预览路径校验也改为有界异步；隔离库 Worker 日志反而出现 130–280 ms 的单批运行（先前记录为 16–101 ms），因此撤回该负优化，恢复原有同步批量校验。撤回后的同一副本 5%→55% 程序跳转为 359/535 ms；固定十次跳点严格全部图片解码为 **6/10**，其中一处始终有 1 张图片没有可用 URL，另三处为 524–599 ms 的尾部延迟。该副本经多轮读写和磁盘预热，以上不是严格同状态 A/B，也没有复现原窗口的滚动条鼠标手势；原窗口约 1.5 秒的完整时序仍未抓到，不能宣称本轮已解决或达成 500 ms 门槛。下一次应在原窗口或同环境隔离实例记录输入→分页→挂载→路径查询队列/运行→首次与全部图片解码，并用真实滚动条操作复验。

## 当次自动化与审查

2026-11-02 再次分段定位：在同一隔离真实库副本上，恢复原分页拖拽预热后，十次跳转仅 8/10 过严格门槛；一次分页用 540 ms、卡片挂载到 613 ms、全部图片解码到 774 ms。另一处 5 秒超时是测量误判：那张卡仅在视口底边露出不足 1 CSS 像素，`loadImmediately=false` 符合设计。基准现要求卡片与视口至少有 1 CSS 像素的交集，且布局槽位与卡片使用同一判定。曾为该样本尝试原图回退，确认无关后已撤回。
