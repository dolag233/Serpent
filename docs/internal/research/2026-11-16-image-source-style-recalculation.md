# Image source updates and style/layout trace investigation

**Date:** 2026-11-16
**Scope:** Primary-source review of HTML image selection, React DOM image mount behavior, Chromium trace instrumentation, and CSS containment. This is a static investigation; it does not establish the cause of the application trace below.

## Finding in brief

The HTML Standard treats assigning an image's `src` as a relevant mutation, including assigning the same value. For immediately obtained images, the image-data update algorithm is entered synchronously; this does not mean that network transfer or decoding runs synchronously. Chromium routes source mutations through image-source selection and `ImageLoader`, with some work handled synchronously and some via a microtask. Chromium has explicit style invalidation when the selected `<picture>` source changes, but that is not evidence that every `src` assignment causes a full style recalculation. React 19.2.7 reassigns `src` or `srcSet` during an image's mount commit to make the browser's `load` event observable to React handlers. This gives a plausible source-update path to measure, but does not by itself explain the trace's total `UpdateLayoutTree` time.

The supplied trace reports `UpdateLayoutTree` at 1515.78 ms after removal of repeated viewport geometry reads, compared with 1507.04 ms before. Those are observations for this workload and build only. The small difference does not identify the work responsible, establish a regression, or generalize to other libraries or machines.

## 1. Image source selection and rendering work

### Standards facts

- The `src`, `srcset`, and `sizes` attributes are relevant mutations. Setting `src` to its previous value is also explicitly relevant and sets the restart-animation flag. When the user agent obtains images immediately, the standard requires a synchronous run of the image-data update algorithm after image creation or a relevant mutation. The algorithm has a synchronous section followed by later work in parallel; this is not a requirement to synchronously fetch or decode the image. ([HTML Standard: obtaining images and reacting to DOM mutations](https://html.spec.whatwg.org/multipage/images.html#when-to-obtain-images), [image-data update algorithm](https://html.spec.whatwg.org/multipage/images.html#updating-the-image-data))
- `loading="lazy"` affects when the user agent obtains an image. It does not make source attributes cease to be relevant mutations. `srcset` width candidates and `sizes` participate in selecting a candidate URL; `sizes="auto"` is permitted for lazy images and uses the rendered concrete object width when available. If an auto-sized image is not being rendered, the previous auto size may be used or `auto` may be ignored. A change to rendered state or concrete width is itself relevant for auto-sizes. ([HTML Standard: responsive images and `sizes`](https://html.spec.whatwg.org/multipage/images.html#sizes-attributes), [relevant mutations](https://html.spec.whatwg.org/multipage/images.html#reacting-to-dom-mutations))
- Therefore `sizes`/`auto` can make layout-derived width relevant to candidate selection when `srcset`/`picture` is used. They do not imply that an application using only a plain `src` has candidate-size work. `display:none` means the element is not being rendered for the `auto` sizing rule; it does not provide a general guarantee that style work is skipped. ([HTML Standard: parsing `sizes`](https://html.spec.whatwg.org/multipage/images.html#parsing-a-sizes-attribute))

### Chromium implementation facts

Blink's `HTMLImageElement::ParseAttribute` routes `src`, `srcset`, and `sizes` mutations through source selection. Its `SelectSourceURL` path explicitly invalidates attribute mapping and marks style for recalculation when the selected `<picture>` source changes; it then updates the image loader. The separate `ImageLoader::UpdateFromElement` path can take an immediate route or enqueue a microtask depending on loading/cache conditions, and updates the image layout object when resource content changes. See Chromium's [`HTMLImageElement`](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/third_party/blink/renderer/core/html/html_image_element.cc) and [`ImageLoader`](https://chromium.googlesource.com/chromium/src.git/+/dfda8156158345d295f7d870772604b154a9fbdb/third_party/blink/renderer/core/loader/image_loader.cc) implementations.

This separates three things that a flame trace can otherwise blur together: source-candidate selection, image resource/layout-object updates, and a document style/layout-tree update. The code proves these paths exist; it does not prove which one dominates the supplied trace. With no `srcset`, `picture`, or `sizes`, responsive candidate selection is not a strong first hypothesis. Repeated `src` assignment remains a testable path because the standard marks it relevant even when the value is unchanged.

## 2. React DOM image mount behavior

In React DOM 19.2.7, `finalizeInitialChildren` returns `true` for `img`, which schedules `commitMount`. In `commitMount`, React deliberately assigns `img.src` when present, otherwise `img.srcSet`. The adjacent comment says this is intended to cause a browser `load` event after the `onLoad` props can be handled; React prefers `src` even with `srcSet` because Firefox does not trigger a new load event when only `srcSet` is assigned. ([React 19.2.7 `ReactFiberConfigDOM.js`](https://raw.githubusercontent.com/facebook/react/v19.2.7/packages/react-dom-bindings/src/client/ReactFiberConfigDOM.js), [`finalizeInitialChildren`](https://raw.githubusercontent.com/facebook/react/v19.2.7/packages/react-dom-bindings/src/client/ReactFiberConfigDOM.js#L587-L605), [`commitMount`](https://raw.githubusercontent.com/facebook/react/v19.2.7/packages/react-dom-bindings/src/client/ReactFiberConfigDOM.js#L763-L807))

This behavior is part of React's image load-event delivery path, not evidence of an accidental render loop. Avoiding it would require changing or bypassing React's host-mount behavior. That could change whether and when `onLoad` runs, especially for cached or already-loaded images, and could break image state ordering. Treat an override as a compatibility experiment only after a trace proves this assignment is material and a focused test covers cached, eager, lazy, `src`, and `srcSet` cases. No product change is recommended from the current evidence.

## 3. Trace instrumentation for invalidation and selector work

The current trace (`devtools.timeline`, stacks, and `UpdateLayoutTree`) shows work and call stacks but lacks style invalidation events. Chromium emits `StyleRecalcInvalidationTracking` under `TRACE_DISABLED_BY_DEFAULT("devtools.timeline.invalidationTracking")`; the trace schema also defines `ScheduleStyleInvalidationTracking` and `StyleInvalidatorInvalidationTracking`. The event payload can include a node ID, reason, changed class/attribute, selector ID, or stack. Add the resulting category name `disabled-by-default-devtools.timeline.invalidationTracking` to `Tracing.start`'s `includedCategories` for a short diagnostic capture. ([Chromium `Node::SetNeedsStyleRecalc`](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/third_party/blink/renderer/core/dom/node.cc), [DevTools trace event types](https://chromium.googlesource.com/devtools/devtools-frontend/+/b88894b14f63f84c460f66cff8918b2b4d079eae/front_end/models/trace/types/TraceEvents.ts), [CDP Tracing domain](https://chromedevtools.github.io/devtools-protocol/tot/Tracing/))

For per-selector timing, Blink emits `SelectorStats` under `TRACE_DISABLED_BY_DEFAULT("blink.debug")`; its payload includes selector text, stylesheet ID, elapsed microseconds, attempts, fast rejects, and matches. The category to include is `disabled-by-default-blink.debug`. Chrome DevTools exposes this as “Enable CSS selector stats (slow)” and documents that it is off by default because it adds recording overhead. Blink's `Document::UpdateStyle` also emits `Document::updateStyle` in `blink_style` with resolver-access and style-engine counters; this can help explain update volume but is not a substitute for per-selector timing. ([Chromium `ElementRuleCollector::DumpAndClearRulesPerfMap`](https://chromium.googlesource.com/chromium/src/third_party/+/445c9018cf2e8389f72703fc2abfeac6ccceb3fd/blink/renderer/core/css/element_rule_collector.cc), [Chrome selector-stats guide](https://developer.chrome.com/docs/devtools/performance/selector-stats), [Chromium `Document::UpdateStyle`](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/third_party/blink/renderer/core/dom/document.cc))

Suggested diagnostic configuration: retain the current `devtools.timeline` category, add invalidation tracking for one short repeatable jump, and collect `blink.debug` only in a separate selector-stat run. Keep the current streaming trace mode and check `tracingComplete.dataLossOccurred`; CDP exposes included categories, buffer settings, and stream completion. These diagnostic categories can increase event volume and perturb timings, especially selector stats, so do not compare their durations directly with the existing low-instrumentation trace.

The pinned `ElementRuleCollector::DumpAndClearRulesPerfMap` producer puts a `selector_timings` array inside the `selector_stats` trace argument. Its numeric keys include `elapsed (us)`, `match_attempts`, `fast_reject_count`, and `match_count`; selectors and stylesheet identifiers must remain private to the in-memory classifier. The current Windows diagnostic observed numeric values at this expected path, while preserving missing-array counts for events without that payload. The first invalidation capture exceeded the 64MiB read cap; the successful diagnostic instead used a 200ms capture with fewer categories. See the [runtime evidence](../development/2026-11-16-canvas-layout-measurement.md); these observations do not identify a product root cause by themselves.

Raw trace fields can contain page URLs, stack locations, frame and node IDs, CSS selectors, and stylesheet identifiers. Keep raw traces local and short-lived. For reports, emit only allowlisted aggregate counts and timing buckets keyed by normalized reason/event type; omit URLs, paths, selectors, IDs, stack frames, and raw `args`.

## 4. Fixed geometry and containment candidates

These are candidates for a controlled A/B, not conclusions about likely gains.

- A fixed-size virtual slot or a grid-defined slot can preserve scroll geometry independently of image intrinsic dimensions. This is the lowest-risk baseline to test because it changes sizing inputs without necessarily skipping the card subtree. Validate selection outlines, captions, overlays, focus, overflow, image aspect-ratio transitions, and scroll-to-item behavior.
- `contain: layout style` on an isolated card subtree may limit style/layout effects from descendants. Layout containment creates an independent formatting context and affects containing blocks/stacking; avoid applying it to a subtree with fixed-position descendants, popovers, or overlays until positioning and stacking are checked. Do not add paint containment casually: it clips ink/scrollable overflow. ([CSS Containment Level 2](https://www.w3.org/TR/css-contain-2/#layout-containment), [paint containment](https://www.w3.org/TR/css-contain-2/#paint-containment))
- `content-visibility: auto` is explicitly intended for off-screen content, but when contents are skipped it also applies size containment. Without a fixed or intrinsic size, scrollbar position and layout can jump; the specification suggests fixed sizing, grid sizing, or `contain-intrinsic-size`. It also specifies that skipped contents are never intersecting from an `IntersectionObserver`'s perspective, and skipped descendants do not trigger `ResizeObserver` size changes until they become unskipped. `scrollIntoView()` uses size-contained geometry while skipping, so post-unskip size changes can affect alignment; a `getBoundingClientRect()` read inside skipped content can force rendering work. ([CSS Containment: `content-visibility: auto`](https://www.w3.org/TR/css-contain-2/#using-content-visibility-auto), [restrictions](https://www.w3.org/TR/css-contain-2/#content-visibility-auto))

For any containment trial, compare the same cold/warm jump and scroll workload with geometry getter counts and trace durations. Include selection/focus, overflow menus, keyboard navigation, `scrollIntoView`, IntersectionObserver/ResizeObserver delivery, resize/zoom, natural image dimensions, and card overlays. A virtualized app already removes many off-screen DOM nodes, so `content-visibility` may add little; that is an inference to test, not a specification claim.

## Evidence limits and next step

The strongest next evidence is a short trace that adds invalidation reasons, followed by an isolated selector-stat trace only if `Recalculate Style`/`UpdateStyle` remains material. Correlate event counts and normalized reasons with React image commits in the same repeatable run. If the extra categories identify image source assignment, test a narrowly instrumented React mount case; if they identify selectors or unrelated DOM mutations, follow that evidence instead. Neither the supplied `UpdateLayoutTree` totals nor the presence of React frames establishes the cause on its own.
